# Sandbox: how the seatbelt profile is assembled, and what it allows by default

> Filling in one of the "not yet done" items from the earlier reports: the generation logic of the sandbox profile and its default allow set.
> The object is still Claude Code v2.1.287; the first-hand evidence comes from the JS corpus `raw/chunks2/` (not from disassembly).
> Related: `06-quirks.en.md` (the permission gate = the JS-side "should the user be asked"), `REPORT-native.en.md` (the CLI itself has no App Sandbox entitlement).

## Conclusions at a glance

1. **The sandbox is off by default.** The verbatim description of the `sandbox.enabled` setting is: `Run Bash commands inside the sandbox. Default: false.` — while it is not enabled, the file read/write rules have no effect at all (see the two `if(!config)` branches in §3).
2. The profile **is not assembled by native code but on the JS side, into an array of strings**, which is then handed to macOS's `sandbox-exec` to execute; on Linux the same code switches to `bwrap` + `seccomp` (the latter is not covered in this report).
3. The profile skeleton comes from **Chrome's sandbox policy**: `(version 1)` + `(deny default (with message "<logTag>"))`, followed by item-by-item allowlisting (process, user-preference, specific Mach services, specific IOKit, specific sysctl, one particular system-socket).
4. **File reads**: with no configuration it is `(allow file-read*)` (everything allowed); with configuration it is still "allowed by default", with `denyRead` and the `allowRead` exceptions layered on top.
5. **File writes**: with no configuration it is `(allow file-write*)` (everything allowed); with configuration it becomes "only what `allowWrite` permits", minus a **built-in write-denylist** — that is the part genuinely worth copying (§4).
6. The built-in write-denylist writes "the agent should not modify its own runtime environment" into the sandbox: shell startup files, git config, `.mcp.json`, `.vscode`/`.idea`, `.claude/commands`, `.claude/agents`, `.git/hooks`.
7. Certain fields **are honored only from user / enterprise-managed / CLI `--settings`; the same-named configuration in project settings is ignored** — preventing a repository from escalating its own privileges.

## 1. Where this lives and how it is executed

- Profile-generating function: `raw/chunks2/0205__chunk-5vadtxaa.js` starting at @730440 (`PV({readConfig, writeConfig, httpProxyPort, socksProxyPort, needsNetworkRestriction, allowUnixSockets, allowAllUnixSockets, allowLocalBinding, allowMachLookup, allowPty, allowGitConfig, enableWeakerNetworkIsolation, allowAppleEvents, logTag})`).
- The file rules are generated by three functions: `OV(readConfig)` (read), `BV(writeConfig)` (write), `vV()` (the built-in write-denylist).
- The assembly helper `_a(kind, ops, set, msg)` emits something of the form:

```scheme
(deny file-write*
 (subpath "/Users/me/project/.git")
 (with message "<logTag>"))
```

- The binary contains both `sandbox-exec` / `sandbox_init` / `seatbelt` and the Linux-side `bwrap` / `seccomp` strings — **one abstraction, two backends**.

## 2. The profile skeleton (verbatim, excerpted in order of appearance)

```scheme
(version 1)
(deny default (with message "<logTag>"))

; Essential permissions - based on Chrome sandbox policy
; Process permissions
(allow process-exec)
(allow process-fork)
(allow process-info* (target same-sandbox))
(allow signal (target same-sandbox))
(allow mach-priv-task-port (target same-sandbox))

; User preferences
(allow user-preference-read)

; Mach IPC - specific services only (no wildcard)
(allow mach-lookup
 (global-name "com.apple.audio.systemsoundserver")
 (global-name "com.apple.distributed_notifications@Uv3")
 (global-name "com.apple.FontObjectsServer")
 (global-name "com.apple.fonts")
 (global-name "com.apple.logd")
 (global-name "com.apple.lsd.mapdb")
 (global-name "com.apple.PowerManagement.control")
 (global-name "com.apple.system.logger")
 (global-name "com.apple.system.notification_center")
 (global-name "com.apple.system.opendirectoryd.libinfo")
 (global-name "com.apple.system.opendirectoryd.membership")
 (global-name "com.apple.bsd.dirhelper")
 (global-name "com.apple.securityd.xpc")
 (global-name "com.apple.coreservices.launchservicesd")
)
```

Optional add-ons (off by default, enabled per setting):

```scheme
; trustd.agent - needed for Go TLS certificate verification (weaker network isolation)
(allow mach-lookup (global-name "com.apple.trustd.agent"))
; Apple Events - opt-in; needed for open/osascript to talk to other apps (appleeventsd)
(allow appleevent-send)
```

The rest also includes (excerpt): `(allow ipc-posix-shm)` (shared memory), `(allow ipc-posix-sem)` (semaphores for Python multiprocessing), `(allow iokit-open …)`, `(allow iokit-get-properties)`, `(allow system-socket (require-all (socket-domain AF_SYSTEM) (socket-protocol 2)))` (explicitly commented "doesn't allow network access"), and a `(allow sysctl-read …)` allowlist.

> Worth learning: **default deny + item-by-item allowlisting**, with "why this entry is needed" written out as comments (the Chrome policy origin, Go TLS needing trustd, Unix semantics needing shared memory). These are the only clues available when troubleshooting later.

## 3. The default behaviour of the read / write rules (key)

```js
function OV(e, r) {          // read rules
  if (!e) return ["(allow file-read*)"];      // no configuration = allow everything
  ...
}
function BV(e, r, n = false) { // write rules
  if (!e) return ["(allow file-write*)"];     // no configuration = allow everything
  ...
}
```

Construction order when configuration is present:

- **Read**: first `(allow file-read*)` → layer on `denyRead` → layer on `allowRead` (exceptions, taking precedence over deny) → filter rules computed by crossing globs against paths → if a deny covers the root or `/`, add `(allow file-read* (literal "/"))` → if any deny exists, add `(allow file-read-metadata (vnode-type DIRECTORY))` (so directories can still be listed) → then layer on a set of unlink/create restrictions.
- **Write**: first allow only the paths in `allowWrite` → then layer on `denyWithinAllow` → then layer on the **built-in write-denylist** → for a number of directory levels, add `(deny file-write-unlink file-write-create …)`.

One detail worth noting: when there are many directory names they get **group-compressed** (multiple entries under the same parent directory are merged into a single `(subpath …)` block, see the `groups`/`rest` of `RV()` and the `fT` / `NV` thresholds), in order to keep the profile length in check — which incidentally shows that this profile has a length budget.

## 4. The built-in write-denylist (verbatim, the part most worth copying)

```js
var pgn = [".gitconfig", ".gitmodules", ".bashrc", ".bash_profile",
           ".zshrc", ".zprofile", ".profile", ".ripgreprc", ".mcp.json"];
var ee  = [".git", ".vscode", ".idea"];
function fgn() { return [...ee.filter(e => e !== ".git"), ".claude/commands", ".claude/agents"]; }
```

Expanded into rules (relative to `process.cwd()`, with `**/` variants generated as well):

```js
for (const g of pgn)     { push(cwd/g);         push(`**/${g}`); }
for (const g of fgn())   { push(cwd/g);         push(`**/${g}/**`); }   // .vscode .idea .claude/commands .claude/agents
push(".git/hooks");      push("**/.git/hooks/**");
if (!allowGitConfig) {   push(".git/config");   push("**/.git/config"); }
```

In other words, once the sandbox is enabled the **agent cannot write**: shell startup files (`.bashrc`/`.zshrc`/…), git config and modules, `.mcp.json`, the VS Code/JetBrains project directories, `.claude/commands` and `.claude/agents` (that is, **its own instructions and sub-agent definitions**), and `.git/hooks` (to prevent hooks from being planted).

> Worth learning: this list is an enumeration of the attack surface of "the agent can modify itself". **Listing its own configuration directories and command definitions as write-denied** is far more reliable than writing "do not modify your own configuration" into the prompt.

## 5. Network

```
When the network needs restricting: do not push("(allow network*)")
  - bind/inbound: any local port      (allow network-bind/inbound (local ip "*:*"))
  - outbound: localhost only          (allow network-outbound (remote ip "localhost:*"))
  - Unix sockets: all of them, or allowlisted by directory
  - proxy ports: HTTP/SOCKS proxies each get bind/inbound/outbound on localhost:<port>
When no restriction is needed: just (allow network*)
```

There is also a **network-violation logger** in the code: `wy(e, r, n, s)` prints `deny network-outbound <host>:<port> (<reason>)`, wrapped by `(e, r) => xp.lookupFor(e)(...)` — which shows that rejected outbound requests are **logged and reported one by one**, rather than failing silently.

There is also a TLS-terminating-proxy configuration (`NetworkConfigSchema`): it supplies the sandbox runtime with a CA certificate and private key, used to terminate TLS inside the sandbox so that **per-request filtering** can see HTTPS request bodies; if none is supplied, the sandbox runtime generates a temporary CA. The original comment specifically notes: on Windows a temporary CA does not pass trust checks, so `/sandbox install` is needed for a persistent CA.

## 6. The settings surface and privilege-escalation protection

The `sandbox` settings (verbatim excerpts):

| Field | Verbatim description (excerpt) |
|---|---|
| `enabled` | `Run Bash commands inside the sandbox. Default: false.` |
| `failIfUnavailable` | `Exit with an error at startup if sandbox.enabled …` |
| `allowWrite` | `Additional paths to allow writing within the sandbox. Merged with paths from Edit(...) allow permission rules.` |
| `denyWrite` | `Additional paths to deny writing within the sandbox. Merged with paths from Edit(...) deny permission rules.` |
| `denyRead` | `Additional paths to deny reading within the sandbox. Merged with paths from Read(...) deny permission rules.` |
| `allowRead` | `Paths to re-allow reading within denyRead regions. Takes precedence over denyRead for matching paths.` |

Privilege-escalation protection (verbatim): **`Only honored from user, managed/policy, or CLI (--settings) settings — project settings (.claude/settings.json and .claude/settings.local.json) are ignored.`** — a configuration file inside the repository cannot grant itself permissions.

## 7. Relationship to the earlier conclusions

- `06-quirks.en.md` is about the **JS permission gate** ("should this tool call ask the user"), whereas this report is about the **process boundary** ("what it can touch once it is running"). The two layers are independent: the former can be rewritten by settings/flags, the latter is enforced by the OS.
- `REPORT-native.en.md` already established that the CLI itself has no App Sandbox entitlement, so this layer of isolation is something it **invokes on its own initiative**; if the sandbox is not enabled (the default), a Bash child process is constrained by the JS permission gate alone.
